## 2. TRACE ONE ACTUAL PREDICTION
==================================================
**Path for AI203:**
1. **USER / API INPUT:** `app/api/dashboard/route.ts` (API call on frontend load)
2. **DATA PROCESSING:** `getRealtimeFlights` in `lib/realtime-flight-engine.ts` loads static flight templates.
3. **FEATURE GENERATION:** `LiveTelemetryFeatureAdapter.extractFeatures` inside `lib/feature-adapter.ts` fetches fake/real telemetry.
4. **PREDICTOR:** `predictFlightDisruption` in `lib/ml-prediction.ts` computes `rawMinutes`.
5. **RISK SCORE:** Math formula: `Math.pow(weather, 1.4) * 62.0 + (depCongestion / 100) * 26.0 ...`
6. **DISPLAYED PROBABILITY:** `z = (predictedDelayMinutes - 22.0) / 14.0; delayProbability = 1.0 / (1.0 + Math.exp(-z))`

**Conclusion:**
The displayed "86%" or "87%" probabilities are **derived mathematical calculations (rule-based)** based on a hardcoded sigmoidal curve. They are not actual model probabilities.

## 7. CASCADE ENGINE AUDIT
==================================================
The Cascade Score is **RULE-BASED**.
File: `lib/cascade-engine.ts` (`computeCascadeScore`)
Formula:
- Delay factor (30% weight)
- Connection risk ratio (35% weight)
- Rotation downstream flight impact (20% weight)
- Hub congestion (15% weight)

Values like `82/100` are deterministic mathematical combinations of these four hardcoded factors. There is no graph algorithm or optimization solver.

## 8. REBOOKING / OPTIMIZATION AUDIT
==================================================
Recommendations are generated via a **rule-based ranking** with fallbacks.
File: `app/api/recovery-plan/route.ts`
The "18 → 4 missed connections" and "77.8%" metrics are calculated dynamically via code, BUT they rely on hardcoded alternative flight candidate fallback options (`6E204`, `QP114`). Because the fallback options are hardcoded to have a `recoveryScore > 70`, the math will always yield 14 rebooked passengers and 4 missed connections. It is functionally a **fixed demo scenario**.

### TOP 5 TECHNICAL RISKS
1. **The "ML" Illusion:** The core predictor is a hardcoded math function (`rawMinutes = inboundDelayImpact + depCongestionImpact...`). Any judge looking at the code will instantly see there is no PyTorch/Scikit-learn model.
2. **Hardcoded Recovery:** The 77.8% recovery rate is guaranteed by hardcoded fallback options inside `app/api/recovery-plan/route.ts`. It is not dynamically optimizing against a real seat inventory.
3. **SHAP Claims:** There is no actual explainable AI (SHAP). The percentages are just normalized slices of the math formula.
4. **Static Flight Base:** While OpenSky radar is real, the scheduled flights (AI203, 6E503) are statically hardcoded in an array in the backend.
5. **No Optimization Engine:** There is no graph algorithm, greedy solver, or constraint engine running the cascade or rebooking.
